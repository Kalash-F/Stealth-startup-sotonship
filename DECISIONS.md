# DECISIONS

Deviations from `plan.md`, contract interpretations, and assumptions. Newest at the bottom.

## Phase 0

- **D0.1 Repo layout: no `tbml-checker/` wrapper.** plan §3.2 shows everything under `tbml-checker/`. The repo root *is* that folder, so `backend/`, `data/`, `web/`, `reports/` sit at the repo root.
- **D0.2 Backend is an installable package.** `backend/pyproject.toml` defines package `tbml`; `make setup` creates `.venv/` and runs `pip install -e "backend[dev]"`, so `from tbml.pipeline import check` works from anywhere with the venv active. `tbml/paths.py` assumes an editable install (it resolves `data/` relative to the source tree).
- **D0.3 Python version.** plan says 3.11+. Developed and tested on 3.13; `requires-python = ">=3.11"`.
- **D0.4 Rule enum source.** plan §4.6 says the `rule` enum is "see §7.2", but there is no §7.2; the rules are R1–R8 in Phase 4 §4.2. `Rule` enum = `PRICE_OUTLIER, QTY_VALUE_IMPLAUSIBLE, PLACEHOLDER_DESC, GEO_INCONSISTENT, ROUTE_NO_ECONOMIC_SENSE, ARITHMETIC_ERROR, RESIDENTIAL_CONSIGNEE, LOW_CONFIDENCE`.
- **D0.5 `Report.lines` shape.** plan §4.7 says `list[{LineItem + EnrichedLine + Benchmark | null}]`. Implemented as `ReportLine`: every `LineItem` field and every `EnrichedLine` field flattened into one object (they share `line_id`), plus `benchmark: Benchmark | null`. Frontend code should read e.g. `report.lines[0].unit_price`, `report.lines[0].hs6`, `report.lines[0].benchmark?.p90`.
- **D0.6 `hs6_candidates` item shape.** `{hs6: str, score: float 0–1}` as model `HS6Candidate`; at most 3 entries ("top 3").
- **D0.7 Nullable means required-but-nullable.** Every field typed `X | null` in §4 must be present in the JSON; its value may be `null`. No field has a default. This is the strictest reading and makes "missing field" tests meaningful.
- **D0.8 Validation added beyond §4 types** (all derived from the §4 notes column): unknown fields rejected (`extra="forbid"`); `country` = 2 upper-case letters; `currency` = 3 upper-case letters; `hs6` = 6 digits; `line_id` = `L<n>`; `Benchmark.route` = `XX-XX` or null; confidences 0–1; `priority_score` 0–100; `n_observations`, `processing_ms` ≥ 0; `Benchmark` bands must satisfy p10 ≤ p25 ≤ median ≤ p75 ≤ p90 (the Phase 3 monotonic requirement, enforced at the contract so a bad band can never be loaded).
- **D0.9 Fixtures are mock.** The benchmark fixture has `is_mock: true` and `sources: ["mock (test fixture)"]`; the invoice fixture has `is_synthetic: true` and company names suffixed "(synthetic)".
- **D0.10 Stub API.** `api.py` already serves `GET /health` and a stub `POST /check` (returns the fixture report) with CORS for the Vite dev server, so frontend work can start before Phase 5. Full Phase 5 endpoints/error handling are not built.
- **D0.11 Extra dependencies declared up front.** `pandas` and `pyarrow` (Phase 3 parquet bands) are in `backend/pyproject.toml` now, so parallel threads don't have to edit the same dependency list.

## Phase 1

- **D1.1 Generator code lives in the package.** Logic is in `backend/tbml/synthetic/` (`catalogue.py`, `generator.py`, `render.py`, `templates/`); `backend/scripts/generate_invoices.py` is a thin CLI. This lets tests import the generator without path hacks.
- **D1.2 Placeholder bands.** Phase 3 bands don't exist yet, so clean prices are sampled from `data/reference/placeholder_bands.json`: approximate global bands, `is_mock: true`, `n_observations: 0`, source "placeholder (approximate, not real trade data)". Units: kg for 731815/090111/740311, l for 220210, u for 852351/610910/847130. When Phase 3 lands, regenerate with `--bands data/benchmarks/bands.parquet` and change `DEFAULT_BANDS` in `generator.py` so `test_committed_dataset_matches_generator` keeps passing. If real bands use a different unit for an HS6, update `bench_per_unit` in `catalogue.py` too.
- **D1.3 FX table.** `data/reference/fx.csv` holds rounded, approximate 2024 annual averages (AED is the USD peg). Rows other than USD/AED say "verify in Phase 3"; the Phase 3 owner should replace them with a cited source.
- **D1.4 Extra ground-truth files.** The `Invoice` contract has no HS6 or USD price, but Phase 3 tests need them. Besides `truth/{id}.json` (pure `Invoice`) and `labels.csv`, the generator writes `lines.csv` (per line: expected `hs6` (empty for placeholder lines), `true_hs6`, `benchmark_unit`, `bench_units_per_unit`, `normalised_quantity`, `unit_price_usd`, `fx_units_per_usd`, `label`) and `invoices.csv` (per invoice: `role` clean/anomalous/hard_negative, labels, template, route, currency).
- **D1.5 `labels.csv` shape.** Columns `invoice_id,line_id,label,hard_negative,detail`. One row per planted anomaly (`line_id` empty for invoice-level anomalies: GEO, RESIDENTIAL, ARITHMETIC sum errors). Hard negatives have no anomaly, so each gets one row with `label` empty, `hard_negative = CLEAN_HARD`, `detail` = kind. Invoices with no row are plain clean.
- **D1.6 Mix.** n=60 → 18 anomalous (30%), 6 hard negative (10%), 36 clean. Each anomaly type appears exactly 4 times at n=60 (14 invoices carry 2 anomalies, 4 carry 1, pairings shuffled and never the same type twice). The 4-per-type target scales up for larger n.
- **D1.7 How anomalies are planted** (thresholds chosen to clear the Phase 4 rule thresholds with margin):
  - `OVER_PRICE` ×3–×1000 median (log-uniform); `UNDER_PRICE` ÷3–÷100 median. Price lines avoid the parity commodities so they don't also look like route anomalies.
  - `QTY_VALUE_IMPLAUSIBLE`: 1–20 printed units with a line total of ~USD 150k–2M, and always ≥ 15× p90 per benchmark unit (R2 ceiling is 10× p90). These lines are necessarily also extreme price outliers, as in the plan's own example.
  - `ROUTE_NO_ECONOMIC_SENSE`: a parity commodity (copper cathodes 740311 or green coffee 090111, exchange-traded so prices are near identical across countries) priced between p75 and p90. **Assumption to re-check in Phase 3** against per-route medians (R5 needs origin/destination medians within ±15%).
  - `ARITHMETIC_ERROR`: half line-level (line total off by max(3–40%, 10 units)), half invoice-level (stated total off by max(3–25%, 10 units)); always beyond R6's 0.5% / 1-unit tolerance. Every other invoice is exact to the cent.
  - `GEO_INCONSISTENT`: half "city of country A, country B" origin text (e.g. "Plzeň, United Kingdom"), half an unexplained third-country origin vs a loading port in the seller's country.
  - `RESIDENTIAL_CONSIGNEE`: consignee is a named private person at a flat/apartment in the buyer country; invoice total ≥ USD 30k.
  - `PLACEHOLDER_DESC`: description replaced by e.g. "Product ABC", "Goods as per contract", "Item 1"; price stays clean; `lines.csv` expects `hs6` = null.
- **D1.8 Explained re-exports are clean.** Real Dubai and coffee trade involves re-exports, so some clean invoices have a third-country origin *with an explanation in the origin text*, e.g. "China (re-exported from Jebel Ali Free Zone, Dubai)". The GEO rule (R4) must treat origin text containing "re-export" or "transhipped" as explained. Without such a phrase, origin ≠ seller country is the planted anomaly.
- **D1.9 Hard negatives** (`CLEAN_HARD`), cycling three kinds: `premium_near_p90` (one non-parity line at 75–95% of the way from p75 to p90 on a log scale, described as Premium/Branded), `bulk_discount_near_p10` (one line between p10 and p25, 1.5–3× the usual top quantity, "bulk order, volume discount applied"), `unusual_route_explained` (third-country origin transhipped through Felixstowe or re-exported from Jebel Ali, stated on the invoice). All stay within p10–p90.
- **D1.10 Templates.** `classic` (serif, "Quantity / Unit / Unit Price / Amount", date "14 March 2024"), `modern` (sans, "Qty / UoM / Rate / Total", "Bill to/Ship to", ISO date), `trade` (monospace boxed form, "Description of Goods / Quantity (with unit) / Unit Price / Value", DD/MM/YYYY, descriptions in upper case). Phase 2 string comparison must be case-insensitive (plan: "normalised equality"). Every page carries a "SYNTHETIC TEST DOCUMENT" footer; truth JSON has `is_synthetic: true`.
- **D1.11 Printed precision.** Unit prices print with 2 dp (≥ 10), 4 dp (≥ 0.01) or 6 dp (< 0.01, needed for heavily under-priced screws); truth stores exactly what is printed.
- **D1.12 Fictional parties.** Company names, street names and postcodes are invented from word lists; city and port names are real so geography checks have something to work with. UK postcodes use the right area for the city but invented districts/units.
- **D1.13 PDFs are not byte-identical across runs** (WeasyPrint embeds a timestamp). The plan's reproducibility check is on truth JSON and `labels.csv`, which are byte-identical; `lines.csv` and `invoices.csv` are too.

## Phase 4

- **D4.1 Rule signature.** Each rule file exposes `check(invoice, enriched, benchmarks, warnings=None) -> list[Flag]`: the plan's three arguments plus an optional list the rule appends skip-warnings to (R1 "add a warning instead"). `run_rules()` keeps the stub's signature and returns sorted flags; `run_rules_with_warnings()` also returns the warnings. `pipeline.py` still calls `run_rules`, so those warnings are not yet in `Report.warnings`. Phase 5 should switch to `run_rules_with_warnings`. No shared schema changed.
- **D4.2 R5 uses a parity list, not per-country medians.** Phase 3 bands are global only (3A notes), so "origin and destination medians within ±15%" cannot be measured yet. `config.yaml` lists `parity_hs6` (740311 copper cathodes, 090111 green coffee: exchange-traded, same assumption the generator makes, D1.7) as the stand-in. If `country_medians: {hs6: {ISO2: median}}` is filled in, the real ±`parity_tolerance_pct` test is used instead. Origin = seller country, destination = consignee (else buyer) country.
- **D4.3 R3 reading.** Fires when a description matches a placeholder pattern, OR when it is under `min_words` words AND the classifier returned no HS6. `high` when it matches a pattern and is unclassified; otherwise `medium`. "Merchandise", "Goods", "Sundry" were added as whole-description patterns because they are one-word placeholders.
- **D4.4 R4 reading and gazetteer.** `data/reference/cities.csv` (about 615 trade cities and ports, written from general knowledge, not an authoritative list) and `countries.csv` (about 100 countries plus aliases such as UAE, P.R. China, Czechia). Names are matched accent- and punctuation-insensitively. Two checks: (a) a city named in the origin text that lies in a different country than the country also named there, `high`; (b) origin country vs the port of loading's country (seller country if the port is unreadable), `medium`. Origin text containing a phrase from `explained_phrases` (re-export, transhipped...) is skipped (D1.8). Cities whose name is also a country ("Singapore", "Hong Kong") are treated as countries.
- **D4.5 R2 reading.** Line value = `unit_price_usd x normalised_quantity` (so it is the benchmark-unit view of the same price R1 sees); ceiling = p90 x normalised quantity x 10. The invoice-level "disproportionate to item count" check is: total USD / number of lines above `max_avg_line_value_usd` (USD 10M, a judgement call, not calibrated). It is skipped when a line-level R2 flag already exists.
- **D4.6 Severities where the plan is silent.** R2 `high` at 10x the ceiling else `medium`; R5 `medium`; R6 `high` when the difference is at least 10%, else `medium`; R7 `medium`, `high` when a residential *consignee* receives more than USD 250k; R8 `low`. Invoice-level R7 threshold is USD 25k (planted anomalies are at least 30k).
- **D4.7 Flags.** `flag_id` is `R<n>-<line_id or INV>` (e.g. `R1-L2`, `R6-INV`). Flags are sorted high, medium, low; rule order breaks ties. Reasons say "item" for unit `u`, and end with a note when the band is mock, so a mock comparison is never presented as real data.
- **D4.8 Scoring.** As the plan: 40/15/5 per flag, cap 100, `review_now` at 60 or more, `review` at 25 to 59, else `low`. All of it, and every rule threshold, is in `backend/tbml/rules/config.yaml`.
- **D4.9 R7 FX.** The USD total uses `data/reference/fx.csv` (`units_per_usd`), falling back to the enriched lines' USD values. This relies on the `fx.csv` / `fx_annual.csv` split from PR #4; this branch carries the same two files so both merge cleanly.
- **D4.10 Lint.** `E501` is ignored for `tbml/rules/` and `tbml/score/`: the plain-English reason strings read better unbroken.
- **D4.11 Truth-data results are optimistic.** Rules run on truth data against the same placeholder bands the generator used, with planted anomalies placed well clear of the thresholds (D1.7). Perfect recall there is a floor for the rules' logic, not the headline number; Phase 6 measures the real pipeline.
